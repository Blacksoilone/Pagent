# 多 Agent 对话工作空间：产品设计初稿

> 状态：讨论阶段草案
>
> 本文记录当前产品构想，不是最终规格，也不是实现计划。文中的部分规则仍然存在矛盾、缺漏或未经验证的假设，后续应先经过数日打磨，再决定实现范围。

## 1. 产品概述

这是一个真正可运行的 Agent 软件：用户可以配置自己的 API Key，与模型对话，并让 Agent 读取项目、搜索资料、调用工具、修改文件和运行命令。

它的主要区别不是单纯支持更多模型、更多工具或更多并发 Agent，而是提供一个可操作的多 Agent 工作空间：

> 复杂工作由多条相对独立的 Agent 对话链共同完成。用户可以查看不同线路，把某条线路中的重要节点按需引入另一条线路的未来对话，并保留来源、历史位置和依赖关系。

产品可以表现为 GUI、TUI、本地 Web 应用、VS Code 插件或 Neovim 插件，但最终应当是一个能够实际完成工作的 Agent 应用，而不是孤立的算法、通用编排框架或单独的插件机制。

## 2. 核心产品观点

当前 Agent 产品通常有两个极端：

1. 所有工作都压在一条不断变长的主对话中；
2. Agent 可以自主调用 subagent，但 subagent 主要作为主 Agent 的内部工具，用户难以直接理解和操纵它们。

本产品尝试提供第三种方式：

> Agent 可以自主委派和并行执行，但用户仍然能够看到并管理不同的工作线路、重要结论和上下文流向。

用户不需要把所有对话都手工整理成知识图谱。普通对话默认压缩成密集的历史节点；只有有意义的节点才提升为重要节点并成为可操作对象。模型可以主动建议或执行提升，用户也可以手动管理。

## 3. 基本对象

### 3.1 工作空间

工作空间包含全局节点、多个项目以及项目内的多条 Agent 链。

```text
工作空间
├── 全局节点与 Skill
├── 项目 A
│   ├── 项目背景
│   └── 多条 Agent 链
└── 项目 B
    ├── 项目背景
    └── 多条 Agent 链
```

### 3.2 项目

项目通常对应一个本地目录、代码仓库或其他工作目录。项目负责保存：

- 文件和工作区状态；
- 项目级背景节点；
- 项目内 Agent 链；
- 工具权限与执行记录；
- 文件变更及其来源节点。

项目不一定必须是代码项目，也可以是研究、写作或资料整理项目，但初版更适合以代码项目为主要场景。

### 3.3 Agent 链

一条链类似当前 OpenCode 的一个 session，是一个持续存在的工作线路。它拥有：

- 对话历史；
- 当前 Agent 配置；
- 使用的模型；
- 工具和权限；
- 可见的祖先节点与显式引入内容；
- 一个末尾虚节点，用于接收下一次用户输入或自动推进。

不同链可以选择不同 Agent。例如：

- 擅长复杂推理的架构分析 Agent；
- 擅长搜索和阅读代码的调查 Agent；
- 擅长修改代码和运行测试的工作 Agent；
- 专门寻找反例的审查 Agent。

链不是临时工具调用，而是用户可以持续进入、查看和继续对话的工作者线路。

### 3.4 普通节点

一次对话构成一个节点：

```text
用户输入
+ 模型输出
+ 工具调用与结果
+ 读取过的文件、网页或其他资源记录
+ 可能产生的文件变更
```

节点按时间和对话依赖形成链：

```text
A1 → A2 → A3 → ○
```

其中 `○` 是当前末尾虚节点。

普通节点默认以小点显示。对话链可能非常长，因此完整内容不应全部展开在视觉界面中。

### 3.5 重要节点

重要节点仍然是一次普通对话，只是被提升了语义和视觉优先级。

重要节点通常表示：

- 阶段性成果；
- 重要观察；
- 事实或证据；
- 技术决策；
- 待解决问题；
- 关键失败；
- 可供其他线路使用的结论。

重要节点必须拥有：

- 标题；
- 当前简要总结；
- 原始对话和工具记录的来源；
- 所属链和节点 ID。

模型可以在认为得到阶段性成果时主动提升节点，用户也可以随时提升或降低节点。提升会触发标题和总结生成；原始对话内容不被改写。

只有重要节点承担复杂交互操作，例如：

- 从此处继续；
- 从此处创建分支；
- 拖到其他链的虚节点；
- 抽象成背景节点；
- 查看来源和依赖；
- 请求模型重新总结。

普通节点仍应允许用户手动提升，否则用户发现重要内容时无法及时固定它。

### 3.6 虚节点

虚节点是尚未发生的下一次 Agent turn 的预留位置，不代表已经产生的历史。

虚节点可以：

- 接收来自其他重要节点的拖拽引用；
- 作为用户下一次输入的位置；
- 作为 Agent 自动恢复或子 Agent 完成后推进的位置；
- 在下一次对话完成后实体化为普通节点。

虚节点不能作为其他节点的父节点，也不应被视为已消费了引用内容。

如果虚节点中引用的来源发生变化，直接更新引用即可，不产生脏传播，因为模型尚未基于这个引用生成输出。

### 3.7 背景节点

背景节点不属于具体链，任何项目链或工作空间链都可以读取。它们不在图上为每条链绘制显式箭头，而是作为作用域背景存在。

背景节点可以存放：

- 项目介绍；
- 用户偏好；
- 术语说明；
- 长期工作规则；
- 跨链共享的事实；
- Skill 或工作方法；
- 重要的全局约束。

背景节点分为普通背景和关键背景。

#### 普通背景节点

普通背景节点可以按需查询，不一定自动进入每次对话。

#### 关键背景节点

关键背景节点具有更强作用域：

- 创建新链时自动加入起始上下文；
- 已存在的链在下一次对话时收到更新通知；
- 用于放置系统级规则、项目约束或必须遵守的长期要求。

关键背景节点更新时，不需要改写所有历史节点，但后续对话需要知道它已发生更新。

### 3.8 全局节点与 Skill

全局空间提供用户可以随时访问的节点和能力。用户可以从弹出框、侧边栏或其他全局面板中，把节点拖入某个项目链的虚节点。

适合成为全局 Skill 的内容包括：

- PostgreSQL 迁移；
- REST API 审查；
- 测试驱动开发；
- 安全审查；
- 技术文档写作；
- 用户自定义工作习惯。

全局节点可以：

- 只作为用户可携带的普通背景；
- 作为 Skill 提供工作方式；
- 作为对所有项目生效的关键背景。

全局节点拖入项目链时，默认只传递摘要、版本和读取入口，不复制整个内容到上下文中。

## 4. 可见性与上下文规则

每一个实体节点只能查看：

1. 它所在链的任意祖先节点；
2. 已经显式引入的跨链重要节点及其允许查询的历史；
3. 适用范围内的背景节点；
4. 当前用户输入和当前 turn 的工具结果。

节点不能看到自己的后代，也不能看到其他线路没有显式引入的内容。这里不是“有权限但默认不显示”，而是该内容不属于当前节点的可见空间。

例如：

```text
B1 → B2 → B3 → B4 → B5
```

如果 A 引用 B3，则 A 只能知道截至 B3 的信息。B4、B5 对 A 完全不可见，包括索引和查询结果。

跨链引用默认不注入完整历史，而注入：

- 来源链 ID 和名称；
- 来源链起始描述；
- 被引用重要节点的标题和总结；
- 来源历史中重要节点各自的一句话摘要；
- 一个只允许沿来源节点祖先方向查询的 API 说明；
- 必要时的来源版本和状态。

模型需要更多细节时，才主动调用查询工具。这样可以避免重复复制上下文，并尽量保持当前链的缓存和前缀稳定。

## 5. 跨链拖拽与分支

### 5.1 拖到链尾虚节点

将 B 的重要节点拖到 A 的末尾虚节点，不是把 B 的完整上下文合并到 A，而是为 A 的下一次对话预留一个惰性上下文引用。

```text
A1 → A2 → A3 → ○

B3◆ ─────────→ ○
```

下一次 A 产生的新节点可以读取 B3 的摘要，并按需查询 B3 的祖先，但看不到 B3 的后代。

### 5.2 拖到历史位置

如果把 B3 拖到 A2：

```text
A1 → A2 → A3
B1 → B2 → B3
```

结果不是修改现有 A2，也不是从 A3 之后增加节点，而是在 A2 的位置生成新的虚节点：

```text
        ┌→ A2 → A3
A1 ─────┤
        └→ A2'○
             ↑
             B3
```

A1 指向两个不同的 A2 位置，其中新的 A2' 还未实体化。用户在 A2' 中继续对话后，它才成为新的实体节点。

其语义是：

> 如果 A 在生成原 A2 时已经知道 B3 的结论，下一步会如何发展？

### 5.3 同链后代拖回祖先位置

如果把 B3 拖到 B2，也会创建一个新的 fork：

```text
        ┌→ B2 → B3
B1 ─────┤
        └→ B2'○
             ↑
             B3
```

这种情况更像“基于已经完成的一次探索，从早期位置重新开始”。模型查询 B3 历史时，应知道哪些历史与新分支共有；查询到共同祖先后应默认停止，避免重复读取无差异的内容。

## 6. Agent 自主 subagent

Agent 可以像 OpenCode 当前的 subagent 机制一样，自主创建临时子任务。

这些临时执行线路用虚线表示：

```text
A4 · ─ ─ 调查调用方 ─ ─┐
A4 · ─ ─ 查询文档 ──────┼→ A5 ·
A4 · ─ ─ 运行测试 ──────┘
```

默认情况下：

- 临时 subagent 只显示为一个压缩节点或虚线支线；
- 子 Agent 完成后，主链自动推进一个节点；
- 主链节点记录这些 subagent 是如何产生结果的；
- 用户可以展开查看完整执行过程；
- 用户可以在必要时把临时线路提升为持续存在的正式链。

临时 subagent 与正式链的差别主要在于生命周期和交互优先级：正式链是用户可持续进入的工作线路，临时 subagent 是主链两个节点之间的自主执行过程。

## 7. 模型与 Agent 配置

每条链可以选择不同的 Agent 配置和模型。链的身份不等于某一个具体模型。

```text
链：缓存方案调查
Agent：架构推理
模型：当前可用模型
```

模型切换、fallback、限流或配置变更不产生重要节点，只显示为两个节点之间的轻量连线气泡：

```text
A12 ◆ ── [模型改变] ── A13 ·
```

不需要区分切换原因。用户点击气泡后可以查看详细信息；默认只显示“发生了改变”。

如果一次模型响应内部发生多次 fallback，仍然只生成一个对话节点，内部尝试记录在节点的运行事件中。

用户也可以主动改变链的 Agent 或模型。是否需要自动 fork、是否保留旧 Agent 的上下文，目前仍需进一步确定；原则上，模型切换不应破坏原有对话链。

## 8. 重要节点和背景节点的操作

### 提升

将普通节点提升为重要节点：

- 生成标题；
- 生成简要总结；
- 允许用户修改标题和总结；
- 允许跨链拖拽和抽象。

### 降低

用户可以将重要节点降低为普通节点，模型不能主动降低重要节点。

旧标题和总结可以缓存一段时间，以便节点重新提升时恢复；已经存在的引用不能因为视觉降级而悄悄消失，需要保留其引用所需的冻结摘要。

### 抽象

将一个重要节点复制成新的背景节点：

```text
重要节点 I7
    ↓ 抽象
背景节点 G3
```

原节点保留，G3 是独立对象。G3 记录其来源是 I7，但之后不自动跟随 I7 更新。

如果 I7 被修改、删除或变脏：

- 不自动修改 G3；
- 不自动删除 G3；
- 不自动使使用 G3 的线路变脏；
- 提醒用户 G3 的来源发生变化；
- 显示哪些节点或线路依赖 G3。

### 标记与视觉管理

用户可以对重要节点、路径和连线进行视觉标记：

- 节点和链改色；
- 路径高亮；
- 箭头注释；
- 自定义标签。

这些标记不会提供给 AI，也不影响上下文和权限。系统提供默认颜色区分不同链，但用户可以随意改色，即使因此难以区分也不需要系统阻止。

## 9. 删除、修改和脏状态

### 9.1 删除

删除实体节点时：

1. 本链后继节点递归删除；
2. 别链已经消费这些节点的后继保持历史，但标记为脏；
3. 如果存在一条链，其起始节点是被删除节点的后继，则该链整体递归删除；
4. 从被递归删除的节点引出的链接关系不保留；
5. 删除操作必须确认。

如果只是虚节点引用了被删除节点，则直接更新或移除该引用，不产生脏状态。

删除最后一个、未被引用、非虚节点时可以采用二次点击确认；其他删除必须输入节点 ID。删除背景节点虽然通常有大量消费者，也只标记脏，不递归删除项目链。

### 9.2 修改

修改逻辑上等于：

```text
删除旧节点及本链后继
+ 在相同位置创建新的节点或虚节点
```

后果基本与删除相同：本链后继递归删除，相关外链历史变脏，已被递归删除节点发出的链接不保留。

但提示词语义不同：

- 删除：来源已经撤回或不存在；
- 修改：来源内容已经变化，请判断是否影响当前结论。

原本指向被修改节点的链接原则上保留，并指向新的版本；指向被删除后继的链接随后继删除而失效。

### 9.3 脏状态

脏不代表历史输出一定错误，而表示：

> 该历史曾经依赖的来源发生了变化，继续工作前应重新判断是否受影响。

来源变化时，消费线路下一次对话只注入简短通知：

```text
你此前引用的节点 B3 已发生变化。
该变化不一定影响当前结论；如有必要，请重新查看 B3 及其祖先。
```

不默认注入新旧内容差异，以避免不相关的信息污染上下文。

### 9.4 背景来源变化

抽象背景节点的来源发生变化时，只提醒背景节点的来源状态，不自动传播到背景节点消费者。

例如：

```text
背景节点 G3 的来源 I7 已被修改。
G3 仍保留抽象时的内容。
```

系统需要能够查看：

- 背景节点来源；
- 来源当前状态；
- 哪些项目、链和节点依赖这个背景节点。

## 10. 文件变更和回滚

如果一个节点产生了文件变更，应有明显但轻量的附属标记，例如节点旁的细线和小气泡：

```text
◆ A12
   └── 修改 4 个文件 · 测试 18/18
```

气泡可以显示：

- 修改了哪些文件；
- diff 规模；
- 测试结果；
- 当前工作区或 worktree；
- 变更是否已经应用到共享工作区。

当用户删除或修改一个产生过文件变更的节点时，必须强制选择：

1. 仅修改图历史，保留当前文件；
2. 修改图历史并回滚文件；
3. 取消操作。

不能提供默认选择后直接执行。

如果用户选择回滚，系统应基于保存的工作区快照或 Git tree 计算恢复，而不是简单反向应用 patch。若后续还有其他节点修改过相同文件，应检测冲突并要求用户处理。

缓存和历史复现应绑定：

```text
对话可见历史
+ 背景版本
+ 工作区快照
+ 跨链引用摘要版本
```

不能因为回到了旧的对话节点，就错误地假设当前工作区也回到了旧状态。

## 11. 用户界面草案

默认界面由多个并行链组成，而不是通用蜘蛛网：

```text
推理链       ···◆·····◆····○
调查链       ·····◆········○
工作链       ····◆······◆··○
审查链       ······◆·······○
```

- 普通节点是密集的小点；
- 重要节点是大点；
- 虚节点显示为空心点或其他轻量标记；
- 临时 subagent 使用虚线；
- 模型改变、文件变更、测试结果使用连线气泡；
- 跨链连接只在相关节点被选中或附近时突出；
- 鼠标靠近密集区域时局部拉开节点间距，方便点击；
- 点击普通节点显示当时用户输入和模型输出的前若干字符，以及读取文件、网页搜索和工具记录；
- 点击重要节点显示标题、总结、来源、依赖和操作；
- 完整历史仍可通过节点详情和查询工具展开。

重要节点、文件变更和跨链来源应有清楚的默认颜色和样式，但用户可以覆盖颜色。

## 12. 与现有 Agent 的差异

本产品不是简单的：

- Chat UI；
- OpenCode 的图形化日志；
- 多 Agent 编排框架；
- 上下文压缩器；
- Prompt 安全网关；
- Git worktree 管理器。

它可以使用这些机制，但用户可感知的核心能力是：

1. 多条可持续进入的 Agent 工作链；
2. 普通历史被压缩为可导航的节点链；
3. 重要节点可以作为有来源的上下文对象；
4. 引用可以被拖到另一个链的未来节点或历史位置；
5. 用户和 Agent 都能参与上下文路由；
6. 来源变化会产生可追踪但不自动夸大的脏通知；
7. 临时 subagent 是可展开的执行支线；
8. 不同链可以使用不同 Agent、模型和工具能力。

## 13. 当前已知问题与待打磨项

本文不把下列问题假装已经解决：

### 13.1 图结构与时间顺序

拖到历史位置后，视觉位置和实际产生时间不同。需要明确如何表达：新节点在拓扑上后来产生，但在对话位置上与旧节点并列。

### 13.2 节点 ID 与重复位置

同一链上可能出现两个视觉上都像 A2 的节点，必须通过稳定 ID、分支名称和视觉位置区分。

### 13.3 脏传播边界

“别链后继节点脏”“起始节点被删除则整链删除”“背景来源变化只提醒”之间还需要形式化依赖类型和传播规则。

### 13.4 引用节点被降低

已经被引用的重要节点如果被降低，原有引用如何显示、是否允许新引用、总结缓存保留多久，还需要确定。

### 13.5 修改后的链接关系

修改节点等价于删除并重建，但哪些链接保留、哪些链接随递归删除而消失，需要更严格的规则。

### 13.6 文件状态与对话状态

回滚涉及 Git、工作区、后续修改和可能的外部副作用。初版需要严格限定可回滚的范围，不能把 shell、网络、数据库等副作用伪装成可完整回滚。

### 13.7 关键背景节点的优先级

关键背景节点类似系统规则，但它们仍由用户编辑。需要明确多个关键背景冲突时的优先级、版本和处理方式。

### 13.8 模型主动操作的信任边界

模型可以主动提升节点、请求链接和创建 subagent，但哪些操作需要用户确认仍未确定。尤其是自动跨链引用、自动修改背景和自动触发文件回滚需要谨慎设计。

### 13.9 缓存与上下文长度

惰性引用可以减少上下文复制，但不能保证所有模型 API 的 prompt cache 都稳定命中。需要将缓存视为优化而非语义保证。

### 13.10 普通节点的压缩方式

普通节点默认只显示摘要片段，但模型和用户如何查看完整内容、摘要是否自动生成、摘要错误如何纠正，仍需要设计。

### 13.11 产品范围

初版需要在 GUI、TUI、本地 Web、VS Code 和 Neovim 等形态中选择一种，不应一开始全部支持。也需要决定首要场景是代码开发、研究、写作还是通用个人 Agent。

## 14. 初版的建议边界

在实现前，建议将初版限制在：

- 一个本地项目；
- 多条持久 Agent 链；
- 一个或少数几个 API 提供商；
- 文件读取、搜索、修改和有限 shell 工具；
- 普通节点、重要节点、虚节点和背景节点；
- 重要节点拖拽到另一条链的末尾虚节点；
- 基于祖先的受限历史查询；
- 简单的模型切换气泡；
- 文件变更气泡和显式回滚选择；
- 临时 subagent 的可展开显示。

历史位置 fork、完整脏传播、全局 Skill、复杂背景版本和多种回滚策略可以在核心链路稳定后逐步加入。

## 15. 当前产品定义

> 这是一个本地优先的多 Agent 对话工作空间。每条 Agent session 是一条由对话节点组成的持续工作链；普通节点被压缩为密集历史，重要节点可以被用户或模型提升。用户可以把重要节点惰性地拖入另一条链的未来位置或历史分支，接收链只能看到显式引入的来源及其祖先。背景节点和全局 Skill 提供跨项目能力，临时 subagent 以可展开虚线支线执行。软件最终服务于真实工作：对话、搜索、文件修改、命令执行、测试和结果选择。

这份文档的作用是固定当前产品直觉，不是冻结最终实现。下一阶段应优先打磨对象关系、可见性、脏传播、文件回滚和 UI 交互，再决定技术方案与实现顺序。
